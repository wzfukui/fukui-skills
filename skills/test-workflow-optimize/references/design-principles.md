# 核心思想与设计理由

## 优化目标是可靠反馈时间

一次开发的反馈时间包含排队、启动、发现测试、构造环境、执行与定位失败。只缩短最后一段，可能仍让开发者为修改一个纯函数等待十几分钟；只减少用例，又可能失去验收价值。

这套方法同时优化两条路径：日常开发运行合理的快速/受影响范围，提交与发布运行必要的完整覆盖。快速档成功回答“这次开发有没有明显问题”，完整档回答“约定的覆盖是否完成”。报告明确区分两种证据。

## 成本由语义决定

纯函数、合同结构和提示词组装往往不需要应用、数据库或密码哈希，但公共自动 fixture 可能让它们付出相同成本。降低公共 fixture 的自动范围、按需导入，通常比单纯增加 worker 更直接。

测试层次按验证对象划分，运行档位按开发场景组织。一个验证 CAS 的 API 测试可以同时属于接口与跨连接范围；分类不是为了强行互斥，而是为了准确选择资源和覆盖。

## 隔离服务于正确性

并行只有在资源独立时才可能稳定提速。独立数据库不一定等于独立数据库实例；同服务器仍可能有 IO 或内部锁竞争，是否分实例由数据和机器预算决定。

把所有测试包在外层事务中回滚，可以降低清理成本，却可能让独立连接读不到数据，或改变提交回调和锁行为。兼容测试可采用回滚，真实跨连接测试保留原语义并进入完整验收。不能把一个项目的兼容名单移植到另一个项目。

## 选择器要能说明为什么

依赖选择是优化，不是完整性证明。静态导入图对反射、动态材料、权限配置、迁移和共享启动逻辑可能不完整。因此选择计划应同时提供依赖路径和保守扩大覆盖的理由；未知输入宁可扩大，不能悄悄忽略。

为新测试更新依赖注册和范围规则，是测试本身的一部分。否则当前“提速”会随着后续开发变成遗漏回归。

## 结果必须可解释

“绿色”需要同时满足：命令确实执行、约定范围被收集、用例实际完成、没有隐藏失败，且源码稳定。选中 3000 项和执行 3000 项是不同证据；setup 失败、worker 崩溃、超时和中断也需要保留。

失败一出现就写出节点与阶段，能缩短定位时间。即使执行速度没有变化，这也能减少开发者等待全部结束后再猜原因的时间。

## 可维护性来自少量稳定入口

保留一个项目认可的运行入口，让本地开发、AI agent 和 CI 共享参数校验、范围选择、隔离和结果格式。工具内部按计划、执行、资源和报告拆分，而不是要求使用者记住一组零散命令。

共享构造器表达明确版本的业务合同，并返回新对象。旧合同回归继续使用旧构造器；新版本不会通过改一个默认 fixture 让所有历史测试“自动适应”。

## 从经验提取机制，数字由项目实测

来源实践中，公共测试配置为纯规则测试引入了数据库和应用成本；拆开后，一组 89 项快速测试约 6 秒完成，并记录无数据库连接。这证明分层反馈的实际价值，不能由此推算几千项全量也获得相同比例提速。

实践还暴露了测试目录 package 化破坏历史 helper 导入、随机参数 ID 影响并行收集、无序 fixture 导致不稳定，以及运行期间源码变化污染验收等问题。可迁移的是相应机制：渐进迁移、稳定 ID、明确查询/构造前提和版本留证。

并行数、超时、慢测试阈值、数据库实例数和事务兼容名单均由目标项目重新测量。来源项目的值不是这份 skill 的默认值；来源实践仍在进行的最终验收也不作为本 skill 已通过的结果。
